# Ka0s KickCD — Code Review Findings

**Verdict: Ship-ready with minor issues.** No critical taint, secret-value, or correctness bugs found. The 12.0 secret-value handling is rigorous and consistently routed through the documented two-step gate. The closed message bus contract is honoured. The schema-driven settings layer is well-factored. Findings below are mostly maintainability hazards, dead code, perf nits, and one missed locale key.

Counts: Critical 0, High 0, Medium 8, Low 11.

---

## Medium

### F-001 `[design] [event-ordering]` Three independent listeners on `PLAYER_REGEN_*` rely on undocumented dispatch order
**`core/State.lua:130-131`, `modules/IconGrid.lua:1490-1491`, `modules/Castbar.lua:1069-1070`** — `core/State.lua` owns the `inCombat` flag write; `IconGrid` and `Castbar` register the same events to refresh visibility. Both modules read `KickCD.State.inCombat` from inside their own handler. WoW dispatches event-frame handlers in registration order, and `core/State.lua` loads first per the TOC, so today the flag is updated before the modules see it — but this is an implicit invariant, not enforced anywhere. **Impact:** if a future TOC reorder pushes `core/State.lua` after a module file (or someone adds a fourth listener that registers earlier), modules will read the *previous-frame* flag value once per transition. The right shape is for State to fan-out via a message (e.g. `KickCD_COMBAT_STATE`) so the dispatch order is explicit, OR to inline the read inside each handler via `IsCombatLockdown()` and accept the one-frame lag the codebase explicitly rejects.

### F-002 `[design] [api]` Bootstrap frames in `core/State.lua` and `core/LSMPatch.lua` register events at file-load time but the codebase otherwise documents `OnEnable` as the registration point
**`core/State.lua:128-140`, `core/LSMPatch.lua:26-62`** — Two side-effect frames run during ADDON_LOADED (file load), not OnInitialize/OnEnable. This is correct for what they do (State must seed from `InCombatLockdown()` at PLAYER_LOGIN; LSMPatch needs `LibStub("AceGUI-3.0")` available which it is post-libs/ load). But the addon's published convention (CLAUDE.md, AceAddon module pattern) is "events live in OnEnable." A reader navigating "where is `PLAYER_REGEN_DISABLED` registered?" will check modules first and have to dig to find the bootstrap frame. **Impact:** maintainability hazard — the next contributor will likely add a fourth `PLAYER_REGEN_*` listener in another module rather than route through the existing one, fragmenting the source of truth. Suggest a comment block at the top of `modules/IconGrid.lua` and `modules/Castbar.lua` cross-referencing State.lua's bootstrap so the indirection is discoverable.

### F-003 `[perf]` UNIT_SPELLCAST_* events registered without unit filter
**`modules/Castbar.lua:1072-1085`, `modules/IconGrid.lua:1493-1503`** — Both modules register `UNIT_SPELLCAST_START`, `..._STOP`, `..._FAILED`, `..._INTERRUPTED`, `..._DELAYED`, `..._CHANNEL_*`, `..._INTERRUPTIBLE` / `..._NOT_INTERRUPTIBLE` for ALL units, then early-return inside the handler when `unit ~= "target"`. In a 25-player raid with constant casts on every party/raid/nameplate slot, this fires the handler thousands of times per minute for nothing. AceEvent does not expose a `RegisterUnitEvent` path; the workaround is a private CreateFrame frame using `Frame:RegisterUnitEvent("UNIT_SPELLCAST_START", "target")`, with the handler dispatching back into the AceEvent module. **Impact:** per-cast event-handler overhead is small but the count is large; in dense combat this is a meaningful chunk of frametime cost the addon doesn't need.

### F-004 `[design] [dead-code]` Three exposed-but-unused module references on `KickCD`
**`settings/Spells.lua:20`, `settings/Profiles.lua:14`, `settings/Panel.lua:1230`** — `KickCD.SettingsSpells`, `KickCD.SettingsProfiles`, and `KickCD.SettingsCategoryID` are written but never read anywhere in the addon's `.lua` files. The only reference to `SettingsCategoryID` is a doc comment in `core/KickCD.lua:836`. **Impact:** the names suggest a public API surface that doesn't exist, misleading future contributors into either (a) extending these or (b) wondering why `SettingsCategoryID` is not used by `OpenSettings` (which goes through `KickCD.Settings.main:GetID()` directly).

### F-005 `[dead-code]` Back-compat `Spells:Register()` and `Profiles:Register()` shims have no callers
**`settings/Spells.lua:957-961`, `settings/Profiles.lua:77-90`** — Both files include "back-compat shim" functions described as "earlier code paths called X:Register() directly." Neither is called anywhere in the addon. **Impact:** dead code; the comments document a migration that has already completed.

### F-006 `[locale] [missing-key]` `L["Cannot open settings during combat."]` referenced but not defined
**`core/KickCD.lua:123`** — The string is referenced inside `COMMANDS["config"]`'s combat guard. `locales/enUS.lua` does not define this key. The fall-back metatable means the literal English string still renders correctly, so the user sees the right text — but if a translator (deDE etc.) is added without first adding the key to `enUS.lua`, the English text will leak through silently. **Impact:** locale completeness drift; trivial fix.

### F-007 `[design] [polluted-record]` Per-spell `_maxC` field in the watched-state record is written but never read
**`modules/Cooldowns.lua:183`** — `Cooldowns:PollSpell` populates the returned record's `_maxC` field with `maxC` from `Compat.GetSpellCharges`, but no consumer reads it (`StateChanged` only diffs `charges`, the IconGrid Apply path only reads `charges`, `DebugDump` doesn't touch it). **Impact:** confusing — a reader assumes `_maxC` carries semantic meaning. Either drop it or surface it (e.g. show `5/3 charges` instead of `3` in DebugDump, or use it to suppress redundant emissions when `cur` matches `maxC` AND was previously below max).

### F-008 `[ux] [naming]` `MAX charges` semantics: `state.charges` of `0` displays no badge but the spell IS unavailable
**`modules/IconGrid.lua:771-777`** — `Icon:Apply` reads `local c = state and state.charges`, then `if cfg.showCharges and c then ... show` — this hides the badge when `c == 0` (because `0` is truthy in Lua, this is actually fine — but `c == nil` correctly hides). The comment claims "Visibility = 'this spell has charges at all'", which is correct. The naming concern is in `Cooldowns.lua:138`: `hasCharges = cur > 0` is computed but the field on the record is named just `charges` (the raw count) — so the IconGrid is reading the count to decide visibility, while `hasCharges` is locally computed and never persisted. The two booleans share semantics; bake the visibility decision into a single named field (`hasChargesNow`?) or document it. **Impact:** subtle — at 0 charges, the badge displays "0" which is informational but `state.ready` is also `false` so the icon body dims; user sees the right thing. Minor.

## Low

### F-009 `[naming]` Mixed convention: half of `core/KickCD.lua`'s slash output uses `L[...]`, half is bare English
**`core/KickCD.lua:105, 162, 168, 175, 193, 204, 244, 470, 481, 494, ...`** — Strings like `"icon grid locked"`, `"Cooldowns module not loaded"`, `"unknown command '%s'"`, `"db not initialized yet"` are bare English; others on lines 123, 292, 315, 401, 425, 430, 441, 446 do go through `L[...]`. README says "English only" so this is a deliberate trade-off, but the inconsistent style means a future translator either localises everything (and has to find them) or risks a half-translated UI.

### F-010 `[naming] [comment-stale]` Comment block at top of `core/KickCD.lua` says "v0.1" but `KickCD.VERSION = "1.0.1"`
**`core/KickCD.lua:1`** — The file-header comment "core/KickCD.lua — KickCD v0.1" no longer matches reality. Same pattern in `modules/Cooldowns.lua:1`, `modules/IconGrid.lua:1`, `core/Util.lua:1`, `core/State.lua` (no version comment at all but is implicitly v0.1), `defaults/Spells.lua:1`, `core/Database.lua` (no version comment), `core/Compat.lua:1`, etc. **Impact:** cosmetic; the real version lives in `KickCD.toc` and `core/KickCD.lua:36`. Either drop the per-file version stamp or auto-update with a release script.

### F-011 `[locale]` 24 strings defined in `enUS.lua` but never referenced in the codebase
**`locales/enUS.lua`** — Confirmed via grep: `L["Arrange icons horizontally or vertically."]`, `L["Bottom"]`, `L["Category"]`, `L["Class"]`, `L["Gap"]`, `L["Internal-message logging"]`, `L["KickCD"]`, `L["Primary anchor"]`, `L["Primary size"]`, `L["Reset"]`, `L["Reset to defaults"]`, `L["Settings not yet registered"]`, `L["Top"]`, `L["Where the primary icon sits relative to the secondaries."]` are unused. (Category names like `L["interrupt"]` ARE used dynamically via `L[cat]` in settings/Spells.lua:550 — those are NOT dead, even though static grep flagged them.) **Impact:** locale file bloat; trivial cleanup.

### F-012 `[comment]` `KickCD.SettingsCategoryID = main:GetID()` written with no usage but documented as "if that hasn't run yet"
**`settings/Panel.lua:1230`, `core/KickCD.lua:836`** — `core/KickCD.lua:836` claims `KickCD.OpenSettings` waits on both `KickCD.SettingsCategoryID` and `KickCD.Settings.main` to be set. In fact `OpenSettings` only checks `self.Settings.main` directly. The doc comment misleads.

### F-013 `[comment]` Doc comment in `Castbar.lua:62-72` references the `lastGridLayout` cache but `current.duration` not documented as the only public field
**`modules/Castbar.lua:60-70`** — The "module-local state" comment block lists `frame`, `current`, `lastGridLayout` but doesn't mention that `current` is a record returned by `Compat.GetCastingInfo` and that mutating it inside `OnInterruptibilityChanged` (line 1173) is intentional. New reader has to chase three call sites to figure out what `current` actually contains.

### F-014 `[design] [coupling]` `KickCD.IconGrid` is set as `KickCD.IconGrid = IconGrid` at the bottom of the module so the Castbar can reach it directly
**`modules/IconGrid.lua:1727`, `modules/Castbar.lua:98-99, 108-109`** — The fallback path in `resolveGridFrame`/`resolvePrimaryIcon` reaches across the module boundary via `KickCD.IconGrid:GetGridFrame()` rather than going through `KickCD:GetModule("IconGrid", true)`. AceAddon's `GetModule` is the documented cross-module accessor; adopting it consistently would (a) match AceAddon idiom and (b) let consumers detect a disabled IconGrid via `module:IsEnabled()`. CLAUDE.md says "Modules don't call each other directly across boundaries" but this exception is a documented escape hatch — fine, but it would read more cleanly as `KickCD:GetModule("IconGrid", true)`.

### F-015 `[perf]` `Castbar:Reskin` re-runs every CONFIG_CHANGED for section "castbar", including the 50ms-throttled color-picker drag commits
**`settings/Panel.lua:782-790`, `modules/Castbar.lua:1226-1240`** — The color picker fires `Helpers.Set` (which fires `KickCD_CONFIG_CHANGED`) at most ~20 Hz under throttle. Each fire calls `Castbar:Reskin` which re-runs ~40 widget calls (SetSize, SetOrientation, all the LSM:Fetch lookups, all the SetBackdrop calls, etc.). The hot path during a sustained color-picker drag is "throttle window → 40 widget calls"; many of those calls are no-ops because only the color changed. CR-17 split was about cast start vs structural; a similar split between "color-only update" and "structural reskin" would shave the per-tick cost during drags. **Impact:** mid- to low-end systems may see frame-rate dips during sustained color-picker drags. Defer fixing until measurement shows it's an actual issue.

### F-016 `[perf]` `BuildCurves` re-creates 3 curves on every `KickCD_CONFIG_CHANGED { section = "icons" }`
**`modules/IconGrid.lua:223-268, 1533`** — Recreating curves involves three CreateCurve calls + several AddPoint calls. Comment at line 222 calls this "cheap" — it is — but every "icons" config change calls it whether `readyAlpha`/`cooldownAlpha`/`cooldownTint` changed or not. Cache-and-compare would skip the rebuild for unrelated config touches (border, font, layout, glow, etc.). Same low-impact note as F-015: don't fix until profiled.

### F-017 `[design]` `Helpers.SetAndRefresh` lives in `settings/Panel.lua` but is the documented single-write-path for slash commands too
**`settings/Panel.lua:1043-1056`, used at `core/KickCD.lua:101, 188`** — Schema-driven slash mutations route through `Settings.Helpers.SetAndRefresh`. The dependency direction is `core/KickCD.lua` (slash dispatcher) → `settings/Panel.lua` (helpers). The TOC loads core/ before settings/, so at `OnInitialize` time `Helpers.SetAndRefresh` is undefined. The fallback at `core/KickCD.lua:99-104` and `:187-192` handles this, but the structure means "the canonical write path lives in a file that loads after the caller." A small helper file `core/Schema.lua` exporting `Set`/`Get`/`SetAndRefresh` (with `settings/Panel.lua` building on it) would put the helper in load-order-correct position. Defer until additional friction surfaces.

### F-018 `[comment]` `core/State.lua:128-140` bootstrap doesn't unregister `PLAYER_LOGIN` after handling
**`core/State.lua:128-140`** — The `boot` frame keeps PLAYER_LOGIN registered for the session (PLAYER_LOGIN fires once per session/reload, so the listener is harmless after the first fire). `core/LSMPatch.lua:29` does `self:UnregisterAllEvents()` immediately on first fire. Inconsistency. Cosmetic.

### F-019 `[ux]` `/kcd reset spells` and the per-spec "Defaults" popup do different things, and the help text doesn't disambiguate
**`core/KickCD.lua:144` "Reset a panel to defaults — `/kcd reset <general|icons|castbar|spells>`", `core/KickCD.lua:476-481`, `settings/Spells.lua:375-401`** — `/kcd reset spells` calls `Database:ResetAllSpells()` (wipes EVERY class+spec), but the panel's "Defaults" button uses `KICKCD_RESET_SPELLS` which only resets the currently-selected spec. A user reading the help text "Reset a panel to defaults" is unlikely to anticipate that the spells panel is the only one where the slash and the panel button do meaningfully different things. The narrower per-spec form lives only at `/kcd spells reset [CLASS SPEC]`. Either align the slash command with the panel button, or add a clarifying line to `/kcd help` for "spells".
